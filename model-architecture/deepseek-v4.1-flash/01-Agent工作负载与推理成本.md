# 01 · Agent 工作负载：为什么输入与历史状态会成为主要成本

> 状态：已完成  
> 深度：基础  
> 论文定位：第 4–6、19 页

## 本篇只回答一个问题

一次工具调用结束后，模型继续工作时，需要处理和保存什么？

## Agent 为什么是 input-heavy 工作负载

普通问答通常只有一次输入和一次输出。Agent 则会循环执行：

```text
读取任务与资料 → 生成工具调用 → 工具返回结果 →
结果加入上下文 → 模型继续处理 → 生成下一步行动
```

代码、日志、网页内容和工具结果会不断加入上下文。任务持续得越久，模型每轮面对的历史通常越多，而当前轮需要生成的内容可能很短。因此，Agent 的成本不只来自生成，还来自处理、保存和恢复不断增长的输入历史。

把后续要学习的机制放回这个循环中，就能看清它们各自负责的位置。下图首次出现的缩写分别是 Causal Encoder-Decoder（CED，因果编码器-解码器）、Compressed Sparse Attention 2（CSA2，压缩稀疏注意力 2）、Key-Value（KV，键值）和 Sliding-Window Attention（SWA，滑动窗口注意力）：

```text
读取任务、代码或工具结果
        ↓
Prefill：处理新增输入 ───────── CED 降低输入计算
        ↓
保存并检索历史状态 ────────── CSA2 减少全局 KV 的重复存储和检索
        ↓
Decode：生成思考或工具调用 ─── DSpark 加速逐 token 生成
        ↓
执行工具，结果加入上下文
        ↓
任务继续或缓存恢复 ────────── SWA Bounded Replay 降低局部状态恢复成本
        ↓
进入下一轮 Prefill
```

这张流程图只用于建立位置感。每项机制还会与其他环节相互配合，具体原理在后续独立笔记中展开。

## 两个计算阶段

### Prefill：处理输入

模型读取输入 token，完成前向计算，并为后续生成建立 KV Cache。

- 首次处理一段长输入时，需要对整段输入执行 prefill。
- 如果已有前缀缓存，只需处理未被缓存的新内容，但还要加载和继续使用已有状态。
- 如果缓存未命中或无法使用，则需要重新处理更多历史。

Agent 会频繁引入工具结果和新资料，因此 prefill 是这篇报告首先要降低的成本。

### Decode：生成输出

Prefill 完成后，模型逐个生成新 token。每生成一个 token，都要读取已有 KV Cache，并把新 token 的状态追加进去。

因此，长上下文不仅影响输入处理，还会增加生成期间读取历史状态的负担。

## 两种缓存形态

### 运行时 KV Cache

当前请求生成时需要直接访问的历史状态。报告重点讨论其中随上下文增长的全局 KV，它长期占用 High Bandwidth Memory（HBM，高带宽内存），并受到容量和数据访问成本的限制。

### 持久 KV Cache

为后续请求或多轮任务复用而保存的前缀状态，通常位于主机内存或 Solid-State Drive（SSD，固态硬盘）。它可以避免重复 prefill，但会带来存储和数据搬运成本。

这两个概念描述的是缓存放在哪里、何时使用；它们不能和 prefill、decode 两个计算阶段混为一谈。

## 后续架构分别解决什么

| Agent 长任务中的问题 | 报告中的主要机制 |
|---|---|
| 长输入的 prefill 计算昂贵 | CED 让大部分输入只经过前半个模型 |
| 多层重复保存全局历史、重复检索 | CSA2 跨层复用全局 KV 和检索结果 |
| 后续索引仍需扫描很长的历史 | 分层稀疏索引缩小后续层的搜索范围 |
| 局部状态的长期保存或精确恢复昂贵 | SWA Bounded Replay 用短回放近似重建状态 |
| 全局 KV 占用较大 | 4-bit Floating Point（FP4，4 位浮点）降低主要全局 KV 的存储精度 |
| 逐 token 生成较慢 | DSpark 通过草稿与验证加速 decode |

## 需要保留的判断

计算量、缓存容量、数据搬运、吞吐和延迟是不同指标。某项机制将 KV Cache 压缩到原来的 1/4，不代表端到端延迟或总部署成本也会下降到 1/4。

本篇的核心结论是：**长任务 Agent 的效率问题，同时存在于输入处理、历史存储、历史检索、状态恢复和输出生成。V4.1-Flash 的各项设计是在分别处理这些环节。**
